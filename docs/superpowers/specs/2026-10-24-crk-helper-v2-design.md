狀態：**2026-10-24 使用者有條件批准設計方向；按本次修訂核對後可實作 P0–P3，P5 尚未批准。**

## 1. 唯一目標與完成邊界

先讓下面這條鏈路可重現、可解釋、可測量：

**辨識地圖 → 根據已儲存意圖選定唯一節點 → 換算座標 → 點擊一次 → 用後續畫面確認同一節點的關卡預覽 → 結束本次工作。**

成功停在 `PREVIEW_CONFIRMED`，畫面仍停留在預覽。不得接著按「進入」、配置角色、啟動戰鬥或施放技能。V2 最小閉環採獨立入口，預設離線，不串到 V1 自動遠征的下一步。

本版處理目前可見、可核對絕對層數與連線的一個普通戰鬥節點，包含從可見入口選擇節點，以及重新開啟已在進行中的節點。層數不硬寫為 1；第一層與較高層都必須有獨立定位證據。沒有層數錨點、節點在畫面外或需要捲動找路時，回報限制並保持零輸入。首領、恢復、裂縫、招募，以及完整地圖探索不在此閉環內。

不進行所有模型重訓、不重寫整個專案、不把既有功能測試數量當作實機合格證明。沿用有效的辨識、來源綁定與本機輸入能力，優先解決它們如何銜接。

## 2. 根本原因與證據等級

### 2.1 已確認的問題

| 問題 | 已核對證據 | 為什麼會卡住 | V2 對應責任 |
|---|---|---|---|
| 座標縮放分散，歷史上 X/Y 逆轉換不一致 | `current-node-size-20261024.json` 記錄：2275×981 的畫面縮到高 414，曾用寬的比例還原 Y，讓底部框到 981.10；目前 `inspect_map` 已補 `scale_y` | 有效節點略微越界，整包地圖遭拒；圖片能看見不等於座標可操作 | 一條可逆、帶來源的座標轉換鏈，統一取代個別推算 |
| 辨識候選沒有通用的操作權限接線 | `applyMapReview` 將節點與邊保留為 `reachable:false`／`connectionVerified:false`；`currentNodeResume` 只為可見頂部入口下、第一層、特定進行中節點提供例外 | 即使找到很多節點，決策器仍找不到唯一可達目標 | 把候選、連線證據、路線意圖組成有限範圍的 `NodeSelectionProof` |

| 畫面分類成功不等於完整閉環成功 | 現存 `gpg-node-preview-analysis.json` 為 `NODE_BATTLE`，但後續還需獨立綁定節點身份；早先報錯為 `previous input result is not confirmed` | 單張辨識測試過關，實際控制仍可卡在結果確認 | 同一個離線回放必須經過辨識、選擇、解析座標、輸入替身、後續確認 |
| 驗收範圍與宣稱曾混淆 | 影片已有 3232 張逐秒切片；目前保存的 pilot 只含開頭 12 張，`accepted:false`；工具仍明列內容／幾何與時序回放未完成 | 開頭入口／選角分類與單張縮放，不能證明地圖點擊閉環 | 指標分開列出資料覆蓋、定位、決策與閉環，禁止把缺測列為通過 |

這些是「第一次驗收前後留下的失敗紀錄＋目前程式」能支持的結論。部分歷史問題已有局部離線修正，**不代表原先那次完整實機流程已修復或已通過 V2 驗收**。

### 2.2 尚未證實、需要測試的風險

- Windows DPI、跨螢幕座標及客戶區原點是否始終處於同一物理像素空間，尚未由實機校準矩陣證明。現有輸入會加上客戶區原點；不能因此斷言所有 DPI 都正確，也不能把 DPI 當作已證實的歷史主因。
- 模擬器工具列、黑邊與內容區偏移是否造成目標定位失準，需要逐個真實畫面核對；只記錄外框尺寸不充分。
- 辨識耗時是否使畫面超過現行 2500ms 新鮮度上限，需要暖機後計時，不能靠增加上限掩蓋。
- 「當時可以到第 2 層」缺少同一次、完整、版本可綁定的輸入與畫面鏈，不能確定是哪個差異造成後來退步。

### 2.3 可重用與暫緩處理

保留 PNG／frameId／雜湊綁定、視窗身份與前景檢查、實際客戶區擷取、本機單次點擊、OCR 與局部圖片比對。保留 V1 既有程式和使用者設定，V2 測試不改寫攻略、隊伍或寶物。

戰後完成節點追蹤、少於五隻隊伍的角色驗證、戰鬥技能輸入及跨區域推進確實仍有缺口，但與這次「停在預覽」的成功條件無關，另列後續，不混入本階段。

### 4.1 必須傳遞的欄位

- `FrameEnvelope`：`frameId`、`imageSha256`、`captureTime`、`windowId`、`processId`、`clientSizePx`、`clientOriginPx`、`dpi`、`geometryVersion`、原始 PNG。影片使用獨立虛擬擷取時鐘，不偽裝成即時畫面。
- `GeometryContext`：原圖大小、內容區 `contentRectPx`、每次裁切起點、實際分析寬高、補邊量、轉換矩陣及逆矩陣、所屬 frameId。所有框和點均標示座標空間。
- `SelectionIntent`：`zone`、`floor`、`column`、`event=battle`、`openMode=select|resume`。來自攻略或明確啟動設定；不能直接從測試標註讀入執行決策。
- `NodeSelectionProof`：兩張觀察 ID／雜湊、絕對層數錨點、符合意圖的唯一節點、前置位置、可見連線、目標內部可點擊區、最新幾何版本。`select` 證明從可見入口或已核對當前位置可達；`resume` 證明該節點確實進行中；兩者不可互相代用。
- `ClickTransaction`：`transactionId`、語意目標身份、來源證明、點擊前畫面、客戶區／桌面點位、送出時間、結果 `not_sent|sent|uncertain`、deadline。`uncertain` 不允許重新送出。
- `PreviewEvidence`：獨立後續畫面、預覽面板與樓層／事件證據、地圖上被選中節點的定位關係、預覽內的控制項、兩張穩定畫面的對照、與 transaction 的匹配結果。控制項只作確認，絕不點擊。

### 4.2 座標轉換原則

分清四種空間：分析圖片 A → 遊戲內容 G → 擷取客戶區 C → 桌面物理像素 D。網頁上的縮圖或 CSS 像素不進入操作計算。

若內容先從客戶區裁切 `(gx, gy)`，再以實際 `sx`／`sy` 縮放並補邊 `(px, py)`：

`cx = gx + (ax - px) / sx`  
`cy = gy + (ay - py) / sy`  
`dx = clientOriginX + cx`  
`dy = clientOriginY + cy`

多段裁切／縮放以矩陣組合，不在不同模組手算。`sx`／`sy` 根據實際整數輸出尺寸計算，避免沿用同一 nominal scale 導致高度誤差。輸入端只在最後一步取整；不以夾到視窗邊緣的方式掩蓋越界。

模擬器視窗與 DPI 變更時產生新的 `geometryVersion`。點擊前變更就丟棄舊點位並重新定位。桌面原點允許負值以支援副螢幕；客戶區點位仍必須在客戶區內。DPI aware／虛擬化差異由 Capture/Input Adapter 邊界校準，Geometry 不猜測。

不同長寬比有兩種情況，分開報告：圖片被拉伸／裁切的壓力測試，以及遊戲真實重新排列介面的測試。後者必須重新找內容區與錨點，不能將整個介面硬拉回固定 16:9。

### 4.3 節點操作證明

兩張獨立、穩定、同一視窗的地圖觀察，必須在區域、絕對層數、欄位、節點類型與連線上相符。此設計建議相隔至少 200ms；目標框在內容座標中 IoU ≥0.95、中心位移不超過 max(2px, 短邊2%) 才算幾何穩定。超過此範圍的可辨識地圖移動屬等待，不沿用舊框。兩張畫面的像素可以完全相同，但不能重複使用同一擷取 ID。候選分數或亮框本身不能變成可達證明。

第一層可使用已辨識的頂部入口；更高層需要當張可見的頂部入口推算、獨立遊戲文字／位置錨點，或此 V2 工作已確認的錨點。只知道「畫面第二排」或只知道攻略想去第幾層，都不算絕對層數證據。本版不加入自動捲動來補足缺失錨點。

使用兩幀內的相同語意位置核對，點擊框只取最新一幀。可見邊的像素支持沿用現有至少 0.85 作為候選門檻，仍需反例校驗，不將 0.85 當成完整安全證明。若門檻不足，只允許針對失敗元件校準並重跑反例，不一律降低所有辨識門檻。

### 4.4 跨畫面狀態機

`WAIT_MAP → MAP_STABLE → TARGET_READY → CLICK_SENT → WAIT_PREVIEW → PREVIEW_STABLE → PREVIEW_CONFIRMED`

- 點擊前需兩張一致地圖；預覽確認也需兩張獨立、相符的後續畫面。
- `sent` 只代表後端確認送出；`PREVIEW_CONFIRMED` 才代表最小閉環成功。
- 明確辨識到預期動畫／載入時可在原交易中等待；不新增點擊。真正 `UNKNOWN`、錯誤預覽或互相衝突的證據立即停止本案例並保存失敗，不把「不明」改名為過場。
- 地圖仍未改變但還在等待期限內，可繼續觀察，不能判定需要再點一次。15 秒內未確認則 `PREVIEW_TIMEOUT`；等待上限根據單調時鐘，不依 CPU 快慢固定幀數。
- 點擊後視窗移動／縮放，不沿用舊座標或強制要求新舊 viewport 相等。重新擷取與定位，仍核對同一語意目標；無法建立身份就保留不確定狀態並停止，絕不重點。
- 預覽的樓層、事件與被選中地圖節點須和交易吻合；相同樓層上的另一個戰鬥節點不算成功。若預覽看不到足以分辨節點的證據，回報 `PREVIEW_IDENTITY_UNPROVEN`。
- 若啟動時已在預覽，只能回報 `ALREADY_PREVIEW`，不冒充完成了一次地圖點擊。此項屬零輸入結果，與閉環成功分開統計。
- 成功後不推進攻略層數，不清除其他 V1 進度，不允許任何後續遊戲輸入。

## 5. 真實影片與失敗資料的使用方法

### 5.1 先切互動片段，不先遍歷全部遠征

使用已下載的影片 `F:/CRK helper/data/video-validation/buAwy1zf2LI/buAwy1zf2LI.mp4`；季 4 用來測共同互動規則，季 7 的 GPG／MuMu 失敗 PNG 用來測實際布局差異。角色差異不納入本閉環。

從影片中人工標註「穩定地圖、所選節點、最後一張操作前畫面、點擊後轉場、第一張預覽、穩定預覽」的完整片段。點擊時刻沒有滑鼠或操作紀錄時，標註為時間區間，不捏造精確輸入時刻。逐秒切片可導航，邊界附近需提高至來源 30fps 核對；切片數量不設上限。

目標至少 30 個不同互動片段，跨至少 3 區域、2 層與2個路線欄位。先凍結 20 個開發、10 個保留驗收片段；以整段互動分組，不把相鄰畫面分到兩邊。保留片段若拿來修正，當次不得再叫未見驗收，需補入新保留片段。若影片無法提供這個範圍，明列缺口，不能降低分母或重複計數湊足。

真實影片只記錄人類採取的分支。只有當 V2 選擇與該片段人工標註的節點吻合、虛擬點擊落在該節點內，回放器才允許讀取該段後續預覽。選錯就失敗，不能仍播放預設的正確結果來讓測試通過。這能驗證觀察與決策契約，仍不證明本機滑鼠真的送達遊戲。

### 5.2 每張三次隨機尺寸、比例與裁切

每張列入該片段的畫面都產生三次可重現的變換，保存 seed、實際尺寸、比例、裁切框和逆矩陣。不得只挑三個固定常數。變換序列也要包含：整段固定布局、點擊前變更布局、點擊後變更布局，不能只做互不相關的單張圖。

正例隨機裁切保留已人工標註的必要錨點；另有會裁掉目標、連線或預覽身份證據的負例。負例的預期結果是明確證據不足且零誤點，不是猜出被裁掉內容。報告必須分開正例閉環成功與負例正確拒絕，不能用大量拒絕案例稀釋失敗。

測試器知道變換只用於產生正確答案及檢查逆轉換；人工標註的內容區、節點 ID、預覽身份不可注入被測辨識器。整體測試也要驗證辨識器自己找出的內容區。

### 5.3 真實視窗矩陣與數據缺口

建議第一版測試目標：客戶區寬 960–2560px、高 540–1440px、長寬比 1.25–2.5 之內的抽樣；DPI 100%、125%、150%、200%。至少覆蓋接近 4:3、16:9、21:9 的真實遊戲布局，包含工具列／黑邊與非零內容偏移。這是待批准的測試範圍，不是目前已支援的宣稱，也不是對範圍內無限組合的保證。

目前有影片 1440×1080、MuMu 1330×750／1751×983、GPG 2275×981／2085×900 等資料。後兩組主要為單張失敗截圖或不同時刻畫面，**不能直接拼成同一次點擊的真實前後序列**。缺少的真實布局序列只能在獲准的最小閉環實機階段補錄；在此之前標為待驗。

### 5.4 審閱補充：兩類變換測試明確分離

以下為本次提出、待批准的契約決定：

**A. 虛擬客戶區測試（每張三次隨機變換適用這一類）**

將影片畫面縮放／改比例／裁切後，視為一張新的虛擬客戶區 PNG。`clientSizePx` 等於該 PNG 的實際尺寸，`clientOriginPx` 由虛擬擷取後端獨立指定。被測程式只收到與真實擷取相同的欄位，不收到原影片到合成圖片的逆矩陣或人工內容框。節點真值與可點擊區由評分器同步變換，但不提供給辨識器。Geometry 的客戶區輸出應落在新的虛擬客戶區內，不是還原成原影片座標。

G1／G2 的最終落點誤差與安全邊距均以該次客戶區物理像素計算；桌面位置則在這個點上加虛擬物理原點。三次變換各自形成一條時間序列，按 §5.2 指定固定布局、點前變更或點後變更的情境；不在每一張任意跳尺寸後假稱是穩定序列。每一個被餵入的畫面仍具備三次隨機變換的紀錄。

**B. 分析前處理測試（額外的座標單元測試）**

先固定客戶區 PNG，再測產品自己執行的內容裁切、分析縮放、補邊及其逆轉換。Geometry 必須取得該次產品實際產生的前處理參數，否則就不能逆轉換；這些參數不是人工標註真值。此類測試的落點要還原到固定客戶區。A/B 使用獨立 case type 與報告，禁止把 A 的資料變換當成產品已知前處理，亦不能將兩類測試混算來增加通過率。

無論 A 或 B，實際遊戲因長寬比改變而重排介面，仍需真實布局序列才能驗證。

### 5.5 審閱補充：回放排程與時鐘

每段互動人工標註 `preClickFrames`、`humanClickInterval`、`postClickFrames`，三者以來源影片 PTS 定位。`preClickFrames` 至少包含兩張相隔 200ms 的穩定地圖，最後一張必須在人工操作區間開始前；`postClickFrames` 從該最後地圖之後的下一個來源畫面開始，保留其間所有轉場，不直接跳到預覽。

回放先依序交付兩張操作前地圖，只在最後操作前畫面所設的 dispatch barrier 接受虛擬點擊。該 barrier 是測試器排程邊界，不暴露人工標註給產品；虛擬輸入必須以最新觀察的節點與落點為依據。只有一次正確點擊才能釋放後續序列；過早、過晚、錯節點或錯落點都失敗，不能仍接收人類成功分支。有效送出後才繼續按來源 PTS 差交付後續畫面；相同來源 PTS 不得換新 ID 假裝成第二張獨立觀察。

這是在已觀察到的人類分支上核對程式決策。因人工點擊時刻可能只是區間，報告列區間及保守的預覽延遲上界，不宣稱已測得遊戲收到 V2 輸入的延遲。預覽延遲上界以最後操作前地圖到第一張穩定預覽的來源時間差計算，不能扣掉人類等待來美化數字。

時間來源分開：

- 功能回放使用可注入的單調虛擬時鐘，依來源 PTS 差推進。15秒預覽 deadline 從 barrier 的虛擬送出時刻起算，該時刻對齊最後操作前地圖；後續來源時間間隔完整保留。畫面新鮮度的過期／未來時間／延遲案例以明確注入延遲測試，不靠修改系統時間。
- 真實分析耗時使用實際單調時鐘計時，包含 PNG 解碼、內容區與座標前處理、必要辨識、觀察組裝及目標解析；暖機另列。它不會被虛擬時鐘暫停成零。G4 必須同時通過功能回放與實際 p95 ≤1500ms 的效能門檻。
- 實機 G5 的 captureTime、dispatchTime、deadline 與新鮮度全部使用同一實際單調時鐘；送出前畫面年齡 ≤2500ms 是獨立硬條件。虛擬時鐘只由離線後端注入，不能進入本機輸入路徑。

## 6. 分階段計畫與出口條件

| 階段 | 工作與交付 | 進入下一階段的條件 |
|---|---|---|
| P0：凍結基準與失敗集 | 保存程式／模型／設定版本與 hash、已知失敗 PNG、歷史錯誤與影片時間索引；先建立5段原始影片候選與標註清單 | 基準可核對、最小失敗案例存在、5段缺口明列；30段20/10凍結移到P4-C入口，不提前宣稱整套G0完成 |
| P1：統一座標 | 建立 Geometry 與 Capture/Input 邊界契約；測裁切、補邊、獨立 X/Y 縮放、DPI、負原點、整數高度誤差 | G1 全過；任何定位越界不得靠 clamp 補救 |
| P2：地圖到唯一選擇 | Map Observer 與 Node Selector 接通，只處理單一可見普通戰鬥節點；先寫拒絕錯路／多解／缺錨點測試 | G2 全過；不得把全部 map candidates 改為 reachable |
| P3：單次點擊到預覽 | 建立 ClickTransaction、Preview Verifier 和獨立最小入口，注入時鐘／影像／輸入替身 | G3 全過；一次交易最多一個節點點擊，成功必須停在預覽 |
| P4-A：原始解析度中間里程碑 | 先用5段真實、未縮放／未裁切的原始影片，完成地圖→節點→虛擬點擊→預覽確認 | 5/5原始序列閉環成功，認知、座標、狀態皆可檢查；只算中間里程碑，不算G4 |
| P4-B：固定縮放中間里程碑 | 對同5段分別跑75%、100%、125%等比例縮放；不混入隨機比例或裁切 | 15/15固定縮放序列通過；只算中間里程碑，不算G4 |

| P5：獲准後的有限實機 | 僅重複最小閉環，補錄不同大小與比例的真實布局；不進入戰鬥 | G5 全過，並保留影片與程式輸入 trace；不自動擴展成遠征 |

實作採小步測試先行：對每個已證實原因先建立會失敗的測試，再改單一責任模組，再重跑該案例與相關回歸。相同元件多次修正仍失敗就回到假設與介面分析，不繼續堆新的特殊門檻。

每個P4里程碑都保存原始／錯誤截圖、辨識輸出、座標疊圖、狀態轉換紀錄、版本／輸入hash與測試結果；成功資料也保留，不只保存失敗數。P0–P3的單元測試仍須包含錯誤座標、重複點擊、錯誤預覽等反例，這不等於提前執行P4-C的正式負例影像集合。

P4-A／B僅分階段調試，不修改第7節G0–G5最終標準。P0–P4-C完成後才提交「可以做最小實機驗收」的證據；P5需另獲恢復實機的明確授權。完整自動遠征是另一個提案，不包含在本文件的批准範圍。
